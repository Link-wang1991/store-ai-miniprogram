# 手机 Web 与小程序闭环同步设计

## 目标

将已确认的手机 Web 优化同步到微信小程序，并修复审查发现的两个闭环缺口：员工/管理者可以真实提交问题，老板可以在“待我处理”看到并处理这些问题。

## 范围

- 修改小程序的“我的”页、独立问题提交页、经营提醒页和 API 客户端。
- 修改手机 Web 预览的“我的”页，使其与小程序使用同一套问题待办语义。
- 修改 Java 服务，为问题提交与问题处理增加最小、可验证的权限边界。
- 不修改 PC 管理后台、小程序底部五栏导航、知识库正式入库规则、生产配置、现有客户导入改动或 AppID/LAN 地址配置。

## 角色规则

| 角色 | 我的工作 | 经营入口 |
| --- | --- | --- |
| 员工 | 我的任务、提交问题 | 无 |
| 店长、管理员、运营 | 我的任务、上报问题 | 待我处理、经营提醒 |
| 老板 | 不显示我的任务或问题提交 | 待我处理、经营提醒 |

- AI 教练和会谈已在底部五栏，不在“我的”页重复展示。
- “管理后台”和“数据切换”从小程序“我的”页移除；既有路由和数据不删除，批量与高风险治理仍由 PC 端承接。

## 问题闭环

```text
员工提交问题 / 管理者上报问题
  → POST /api/pending-questions
  → 当前门店 pending_questions（status=pending）
  → 老板/店长/管理员在待我处理查看、指派、确认、解决或升级
  → 处理结果写回 pending_questions
```

问题上报只进入待处理队列，不创建知识库文档、知识片段或经验审核候选。知识库仍只接受已确认资料或人工审核通过的候选。

## 后端权限

- 所有已登录的非老板角色可以创建自己门店的问题；内容长度为 2–2000 个字符。
- 老板不创建上报问题；直接访问小程序提交页会返回“我的”，后端也拒绝老板创建。
- 老板、店长、管理员可以查看本店全部问题并执行指派。
- 只有老板、店长、管理员，或被明确指派的处理人，才能确认、解决或升级问题。
- 运营只获得经营提醒的只读能力，不通过修改全局 `isAdmin()` 获得客户、人员、数据生命周期等其他管理权限。

## 待我处理与经营提醒

- 老板“待我处理”统计未关闭的 `pending_questions`，并进入问题处理页。
- 店长、管理员、运营“待我处理”继续指向本人正式任务，避免把员工执行任务与经营决策混为一类。
- 经营提醒显示 `critical + warning`；无高风险但有警告时显示“X 项待关注”，两者均为 0 时显示“运营状态正常”。
- 经营提醒接口仅向 `owner`、`manager`、`admin`、`operator` 开放，不扩大其他端点的角色范围。

## 错误处理与兼容

- 用户身份、任务数、问题数和经营提醒分别读取；任一读取失败不以“0”或“经营正常”替代。
- 小程序新增页面前先在 `app.config.ts` 注册；页面直接访问时仍校验登录与角色。
- 保留既有管理页面路由，避免旧链接与现有数据失效；“我的”页不再提供旧管理中心入口。
- 现有未提交的 `project.config.json`、客户 Word 导入页、`api.ts` 导入注释与 `constants.ts` 局域网地址不作为本轮修改目标。

## 验收

- 员工、店长/管理员/运营、老板的“我的”页入口满足角色矩阵。
- “提交问题/上报问题”不再跳到 AI 教练；成功提交后创建一条待处理问题，且不写知识库。
- 老板待我处理数量与问题处理页未关闭问题数一致。
- 未授权者不能指派、确认、解决或升级不属于自己的问题。
- 运营可读取经营提醒，但不能因本轮获得全局管理员权限。
- 小程序 `npm run typecheck`、`npm run build:weapp`，Java `./mvnw test` 与 `./mvnw -DskipTests compile` 通过。
